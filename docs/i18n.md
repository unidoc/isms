# Internationalization

The ISMS web app is localizable. This document is the contract: how locales are
resolved, how to add one, and where the seams are.

Related: [`web/src/locales/README.md`](../web/src/locales/README.md) holds the key
naming convention and the rules translators and extractors work to.

## The two halves

**The web app owns the keyspace.** Every string a browser renders — UI copy,
enum labels, and eventually API error messages and notification titles — is
translated from `web/src/locales/`. One keyspace means one place a translator
works.

**The server owns only what it pushes outward.** Email and Slack/Matrix messages
are delivered when no client exists to render them, so those need a server-side
catalog. Everything a client can render, a client renders: the API emits stable
error codes rather than translated prose.

In-app notifications are the one part of that not yet built. `notifications.title`
and `body` are still plain `TEXT`, written pre-rendered in English, and a row once
written can never be retranslated. Moving them to a key plus parameters is a
separate migration (#220); until it lands, read the paragraph above as the target
architecture for notifications rather than a description of the schema.

The Go package `internal/isms/i18n` is the single source of truth for *which*
locales exist. The frontend seeds itself from `GET /config` rather than
hardcoding a list, so the two cannot drift.

## Locale resolution

Highest precedence first:

1. **`users.locale`** — the user's explicit choice, from the database, so it
   survives a change of device. Exposed as `locale_preference` on `GET /me`;
   `null` means "following the org default", which is what lets the picker show
   *Org default* rather than a concrete language.
2. **`localStorage.isms_locale`** — pre-login and anonymous pages.
3. **`navigator.languages`** — in the browser's own order of preference. The
   server does the equivalent with `Accept-Language`, honouring q-values.
4. **The organization default** — the `default_locale` setting, editable by an
   admin.
5. **`en`** — the fallback, always bundled and always complete.

Matching is region-tolerant in both directions: `id` resolves to `id-ID`, and
`pt-BR` resolves to `pt-PT` if that is what ships. A tag that matches nothing
falls through to the next signal rather than being applied — so a stale stored
value for a dropped locale renders English instead of raw keys.

Malformed tags are rejected by the server with a 400, and only *simple* tags get
the fallback treatment: anything naming a script, variant or extension
(`id-Latn-ID-x-junk`) is an error. `negotiate()` in `web/src/i18n.js` enforces
the same restriction on the client, because `navigator.languages` and a stored
tag are uncontrolled input too: an over-specified tag falls through to the next
signal rather than being answered with a regional bundle. The locale picker must
therefore send tags straight from `GET /config` → `locales[].tag`, never a tag it
composed itself.

## API surface

| Endpoint | Field | Meaning |
|---|---|---|
| `GET /config` | `locales[]` | `{tag, name}`; `name` is the endonym — build the picker from this |
| `GET /config` | `default_locale` | the org default, already overridden by `Accept-Language` server-side |
| `GET /me` | `locale` | the resolved locale — what to render in |
| `GET /me` | `locale_preference` | the raw choice; `null` = following the org default |
| `PUT /auth/profile` | `{locale}` | omit = unchanged, `""` = clear to the org default, bad tag = 400 |

`PUT /auth/profile` takes `name` as an optional pointer, so a locale-only update
is `{"locale":"id-ID"}`. Do **not** resend the current name alongside it — that
is a lost-update race against a concurrent rename.

## Adding a locale

1. **Register it server-side** — add the tag and its endonym to the supported map
   in `internal/isms/i18n/locale.go`, and extend `locale_test.go`.
2. **Settle the ISO vocabulary before you translate a single value.** The audit
   terms (nonconformity, corrective action, opportunity for improvement,
   conformity) and the information-classification levels are the ones a fluent
   translator gets wrong invisibly, because the wrong choice reads perfectly.
   `web/src/locales/README.md` has the procedure, a language-independent term
   checklist keyed to the clauses of the standard, the three traps that recur
   across languages, and a worked example. Take the terms from your language's
   national adoption of ISO/IEC 27001 or 9001, and record your table there —
   this is a step, not a suggestion: two of the three Indonesian terms it
   catches were wrong on the first pass.
3. **Copy the message bundle** — `cp -r web/src/locales/en web/src/locales/<tag>`
   and translate the values. Keep the filenames and the keys; change only the
   right-hand side.
4. **Register the loader** — add one line to the `loaders` map in
   `web/src/i18n.js`:
   ```js
   '<tag>': () => import('./locales/<tag>/index.js'),
   ```
   Locales are lazy-loaded as separate chunks, so locale N+1 costs nothing to
   users who do not select it. `en` is the exception: it is bundled, because the
   fallback must always be resident.
5. **Check the keyset** — run `npm test` in `web/`. `test/localeKeyset.test.js`
   compares every locale directory against `en` and runs in CI with the rest of
   the suite. Missing keys are a warning: `fallbackLocale` renders them in
   English, and a translation lagging by a few keys must not block an unrelated
   PR. Extra keys **fail** — they are typos or stale keys with no English
   counterpart.
6. **QA the layout.** Translated copy is routinely 20–25% longer than English.
   Check table headers, status badges, the sidebar and button rows for overflow.

## The five seams

No component formats a date, derives a label from an enum value, or holds a
literal. Each category of translatable thing has exactly one implementation:

| Seam | Module |
|---|---|
| UI copy | `useI18n()` from vue-i18n; `t` exported from `@/i18n` for plain `.js` modules |
| Enum labels | `composables/useEnumLabel.js` |
| Dates and numbers | `composables/useFormat.js` |
| Relative time | `useFormat().relative()`, backed by `Intl.RelativeTimeFormat` |
| Region names | `Intl.DisplayNames`, so country names need no translation file in any language |

Enum labels are keyed `common.enum.<group>.<db_value>`, with the group named
after the notification param that interpolates it where one does, and after the
column otherwise. `status` is deliberately one flat group across every register.
The full rule, and the escape hatch if a language needs per-register status
wording, is in [`web/src/locales/README.md`](../web/src/locales/README.md).

`useI18n()` needs an active component instance, so it is unavailable in `api.js`,
`utils.js` and router guards. Those import the global scope instead:

```js
import { t } from '@/i18n'
```

Same keyspace, no second mechanism.

## Out of scope

**Document and template content.** Templates load from `ISMS_TEMPLATE_PATH` as a
separate git repository; folder names, `.title` files and markdown bodies are all
template-maintainer choices. A Portuguese ISO 9001 template directory needs zero
code changes. Do not add locale awareness to the document engine — templates are
already the correct seam, and the core stays standard-agnostic.

**User-authored content** — document bodies, comments, risk descriptions. That is
organization-owned data, not product copy.

**RTL.** No right-to-left locale is requested. `dir` support is a layout project,
not a translation one.

## API error codes

HTTP error responses are one of the two surfaces where the client renders and
the server does not (the other is notifications). The server emits a stable
`code` plus a closed set of `params`; the browser renders the sentence from
`common.error.<code>` in its own locale.

```json
{ "message": "risk not found", "code": "not_found", "params": { "entity": "risk" } }
```

`message` stays populated in English and always will. `internal/isms/client/client.go`
dumps the raw response body into CLI error output, so an empty or code-only
`message` breaks every CLI error message and every server log line at once.
`code` and `params` are purely additive: a client that ignores them behaves
exactly as it does today.

One consequence worth knowing before 1.5 converts anything: because the CLI
prints the whole body rather than decoding it, a converted error reads
`API error 404: {"message":"risk not found","code":"not_found",…}` where today
it reads `API error 404: {"message":"risk not found"}`. The wire shape is now
fixed, so decoding `message` in `client.go` is a one-line improvement — it
belongs with the call-site conversion, not ahead of it.

### Emitting one

`internal/isms/api/errors.go` holds the catalogue and the helper:

```go
return apiError(http.StatusNotFound, CodeNotFound, Entity("risk"))
return apiError(http.StatusBadRequest, CodeRequired, Field("title"))
return errNotFound("risk")   // the three common families have wrappers
```

The English text comes from `errorMessages`, keyed by the same code. So the
English sentence lives in Go — which is what keeps CLI output and server logs
readable with no extra machinery — while every other language lives in the web
locale files. One keyspace, one translator workflow.

`apiError` and `echo.NewHTTPError` coexist deliberately. Call sites convert per
module; an unconverted site is indistinguishable to an old client from a
converted one.

### The closed param set

Four names, each with exactly one lookup rule on the client:

| Param | Value | Client resolves through |
|---|---|---|
| `entity` | snake_case identifier (`corrective_action`) | `common.entity_inline.<value>` |
| `field` | the API's own JSON field name (`path_pattern`) | `common.field.<value>` |
| `status` | a member of the `status` enum group | `common.enum_inline.status.<value>` |
| `count` | a number | spliced raw — it is not an identifier |
| `value` | the caller's own input, echoed back | spliced raw — it is not drawn from any set |

`entity` and `field` are humanised in the English `message` — `Field("path_pattern")`
renders "path pattern is required" — while the wire keeps the identifier the
client looks up. Both come out of the same call, so the two cannot disagree.
De-slugging alone is not enough for an acronym (`oidc_provider` would become
"oidc provider", regressing today's "OIDC provider not found"), so
`paramMessageOverrides` carries the English prose for those, and a test holds
each override equal to what the `en` catalogue says.

**`value` is not a fifth flavour of identifier.** The lookup-or-raw question
has two answers and the first four names only covered one of them.
`"invalid status: draught"` echoes what the caller sent so they can see their
typo; that string is by construction *not* an enum member, so routing it
through `status` would mean every catalogue lookup misses and an unbounded,
caller-supplied string is spliced into an otherwise translated sentence — the
leak this catalogue exists to prevent, wearing a translation's clothes. Use
`value` only for input the caller supplied; anything drawn from a known set
belongs in `Entity`, `Field` or `Status`, where the client can translate it.

`common.field.*` is authored lowercase, like `common.entity_inline.*` and
unlike `common.entity.*`. Every sentence in this catalogue is lowercase
throughout, and `{field}` leads two of them, so a capitalised value would make
the browser say "Title is required" where the CLI says "title is required" —
same code, same language, two texts.

**`entity` resolves through `common.entity_inline.*`, not `common.entity.*`.**
Error sentences interpolate mid-sentence ("risk not found"), and the inline
form is a separately authored string rather than a lowercasing of the
standalone one — which words a language capitalises mid-sentence is a property
of that language. `common.entity.*` is for the badge and the page heading.

`status` is not an arbitrary param name: it is the name of an existing enum
group, which is what lets the client derive the lookup path from the param name
with no second mapping. That is the same convention the notification params
use.

The set is closed at compile time, not by convention: `apiError` takes
`...ErrorParam`, and an `ErrorParam` can only be built by `Entity`, `Field`,
`Status` or `Count`. A fifth param name means either a fifth lookup rule or an
identifier spliced raw into an otherwise translated sentence, so adding one is
a design decision rather than a call-site convenience.

### Which literals get a code

Not all of them. Of the 328 distinct string literals passed to
`echo.NewHTTPError` in `internal/isms/api`:

- **Internal wraps stay as they are, permanently.** `"creating user: "`,
  `"hashing password"`, `"reading document: "` and their ~90 siblings are 500s
  describing a server fault, not copy anyone is meant to act on. They are not
  user-facing text and get no code.
- **Operator configuration messages stay too** — `"WebAuthn not configured
  (set ISMS_BASE_URL)"`, `"email not configured (SMTP_HOST)"`,
  `"ISMS_DATA_DIR not configured"`, the OIDC and Cloudflare Access variants.
  These are read by whoever deploys the server, in a log, in English.
- **Three parameterised families absorb the long tail**: `not_found{entity}`
  (~110 sites), `invalid_entity_id{entity}` (~20), `required{field}` (~8).
- **Everything else gets one code per distinct sentence.** In particular the
  authorization messages are *not* collapsed into a single `forbidden`:
  `message` is generated from the code's template, so a generic code would
  degrade "only the document author can accept suggestions" to "forbidden" in
  the CLI and in the logs. That is why the catalogue is dozens of codes rather
  than a dozen.

A few literals were folded into an existing code rather than given their own,
because they say the same thing in different words. Each changes the English
`message` slightly at those call sites; that is deliberate, not an oversight
to restore during conversion:

- `"user email required"` (3 sites) → `required{field: email}`
- `"user is not a member of this organization"` (2) → `not_org_member`, the
  same code as the eight `"not a member of this organization"` sites

`"review is already <status>"` (`api_collab.go:442,1612`) is **not** folded
into `review_wrong_status`: dropping "already" turns a statement about a
transition that has already happened into one about the current state, which
is a different sentence. It has its own code, `review_already_status`.
`"review is not in changes_requested state"` (`:1508`) is a third sentence
again and stays uncatalogued until 1.5 converts it.

`"push requires manager or admin role"` is deliberately **absent**. Its only
two call sites are in `api_git.go`, the git wire protocol — consumed by
`git push`, never rendered by a browser. Its key would be one no client could
ever read, so by the operator-messages rule above it stays on
`echo.NewHTTPError`.

The initial catalogue covers every in-scope literal appearing at **two or more**
call sites. A single-occurrence sentence gets its code when its call site is
converted, in the same commit as its `common.error.*` key — a code invented
ahead of that is a guess about wording that the conversion would revise.

### What CI enforces

`internal/isms/api/errors_test.go` runs in the database-free test job:

| Check | Fails when |
|---|---|
| every code has an English key | a code ships with no `common.error.*` entry |
| every English key has a code | a renamed code leaves a dead entry translators keep translating |
| placeholders match, **in every locale** | a translation invents a slot (renders blank) or drops one (loses what it named) |
| params are within the closed set | a template names something the client has no lookup rule for |
| every `Code*` constant is catalogued | a constant is declared but has no English template |
| param values have catalogue keys | `Entity("x")` / `Field("x")` / `Status("x")` at any call site has no key to resolve through |
| the `en` catalogue matches the Go templates | the English sentence, which is written twice, drifts in wording between them |
| acronym overrides match the catalogue | `paramMessageOverrides` and the `en` locale disagree on an identifier's prose |
| declared statuses have inline forms | a code carrying `{status}` can send a member `common.enum_inline.status` has no key for |
| every `{status}` code is declared | a new status-carrying code ships with no `errorStatusValues` entry, making the check above vacuous |
| wire shape | an edit to `errorBody`, or an Echo upgrade, flattens the response back to `{"message": …}` and drops `code` |

The placeholder check runs against **every** locale rather than `en` alone.
`en` is also the fallback, so it renders correctly whatever its slots say; the
locale this seam exists to protect is the one nobody on the team reads. A
locale *missing* a code is a warning rather than a failure — `fallbackLocale`
covers it, and a translation lagging a few keys must not block an unrelated PR.
That is the same policy `web/test/localeKeyset.test.js` applies.

The param-value check parses the package (rather than grepping it — a regex
also matches an example written inside a doc comment, and a check that fires on
its own documentation gets deleted rather than fixed) and reads the literal
arguments to `Entity`, `Field` and `Status`. It passes vacuously until the
first call site is converted, which is the intent: it starts working the moment
there is anything to check.

**Its blind spot is stated rather than hidden.** It sees only *literal*
arguments, and `Status` is handed a variable at every real call site
(`review.Status`) — so for the one param whose values are least predictable,
the scan finds nothing. That half is covered instead by `errorStatusValues`,
which declares per code which members it can send, checked against
`common.enum_inline.status` and pinned so a new status-carrying code cannot
ship without an entry. This is the same shape as the per-key notification param
table, and for the same reason: a vocabulary of names the backend knows is not
a statement about what *this* sentence is handed.

One thing stays unenforced. `errorStatusValues` is hand-maintained, so an entry
that omits a status a call site can actually send is caught only when someone
hits that path. That direction is the one that fails loudly (a capitalised
label mid-sentence), rather than silently.
